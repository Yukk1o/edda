# 不变量

> 表可以改、代码可以重写，这七条不能破。每一条都必须在某个阶段被一条可执行的验收覆盖。

## 清单

| # | 不变量 | 一句话 | 破了会怎样 | 由谁保证 |
|---|---|---|---|---|
| I1 | 名额守恒 | 可售 + 冻结 + 已售 = 总名额 | 超卖或少卖，且无法自愈 | 条件更新 + 对账 |
| I2 | 金额自洽 | 实付 = 总额 − 优惠，且都 ≥ 0 | 对账永远对不平 | 落库前断言 |
| I3 | 一券一单 | 一张用户券最多被一张订单核销 | 同一张券抵扣两次 | 持久层唯一性 + 状态机 |
| I4 | 一单一授权 | 同账号同课程最多一条有效授权 | 重复授权、重复占名额 | 持久层唯一性（仅有效态） |
| I5 | 进度不可逆 | 已看时长只增不减 | 刷回进度绕过退款闸门 | 写入时取最大值 |
| I6 | 支付幂等 | 同渠道同交易号只生效一次 | 重复回调 → 重复授权 | 持久层唯一性 |
| I7 | 下单幂等 | 同账号同幂等键只出一张单 | 重复下单、重复扣名额 | 持久层唯一性 + 冲突返回原单 |

## 四层防线

| 层 | 作用 | 局限 |
|---|---|---|
| 1. 领域断言 | 落库前校验，最快 | 只在单进程单次调用有效 |
| 2. 持久层唯一性 | 并发下唯一可靠的保证 | 需要提前设计唯一范围 |
| 3. 状态机 | 阻止非法迁移 | 只在状态迁移路径上生效 |
| 4. 定时对账 | 事后兜底，唯一能发现"静默不一致"的手段 | 滞后，且需要人工处理差异 |

只有第 1 层的系统迟早不一致；只有第 4 层的系统意味着天天在对账。

## 怎么验证

每条不变量对应一个可执行的检查，落地位置见 issues 036~038。

| # | 验收方式 |
|---|---|
| I1 | 并发抢购后比对三列之和与总名额；对账任务每日全量比对 |
| I2 | 随机抽 100 单，重算 `总额 − 优惠` 与实付比对 |
| I3 | 同一券并发核销 20 次，成功次数必须为 1 |
| I4 | 重复投递支付回调 3 次，有效授权仍为 1 条 |
| I5 | 上报一个更小的已看时长，读回值不得倒退 |
| I6 | 同一交易号回调 3 次，支付记录仍为 1 条 |
| I7 | 同幂等键并发 50 次，订单数为 1、名额冻结量为 1 |

## 违反时的处理顺序

发现不一致时**不要先改代码**，按这个顺序：

1. 先确认能观测到（有没有查询/对账能看到，没有就先补观测）
2. 评估影响面（多少数据、是否涉及资金）
3. 判断是"设计漏了"还是"实现错了"
4. 设计漏了 → 补一条 ADR；实现错了 → 补一条测试
5. 最后才是修数据，且修数据必须有脚本、可回滚、可审计
