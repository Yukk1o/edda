# 演进路线

> 三条线并行推进，但**一次只动一条线的一个点**：加功能时不动架构，动架构时不加功能。

## 里程碑

| 里程碑 | 功能 | 新增组件 | 形态 | 验收一句话 |
|---|---|---|---|---|
| M0 骨架 | — | 无 | 单体 | 能起、能通、ArchUnit 绿 |
| M1 v0 闭环 | 登录→券→名额→下单→支付→授权→超时→退款 | 无 | 单体 | 七条不变量成立 |
| M2 v0.1 评论 | 发布、审核、可见性、申诉 | 无 | 单体 | 违规内容不对外可见 |
| M3 对账 | 三个定时对账任务 | 无（用 `@Scheduled`） | 单体 | 人为制造偏差能被报出 |
| M4 v1 读优化 | 课程搜索、详情热点 | **Redis**（条件满足才加） | 单体 | 详情 P95 降到原来的 1/5 |
| M5 v1.1 热点 | 秒杀 / 拼团 | **Redis + MQ** | 单体（预演拆分） | 1000 并发抢 100，不超卖不少卖 |
| M6 可拆性 | 无新功能 | trace、契约测试、场景脚本 | 单体多进程 | 一次请求跨进程可追、脚本全绿 |
| M7 拆 course | — | 注册中心、网关（最小形态） | 2 进程 | 拆分后回归全绿，P95 不变差 |
| M8 拆 auth | — | — | 3 进程 | 同上 |
| M9 拆 coupon / enroll | — | — | 5 进程 | 同上 |
| M10 拆 payment / order | — | MQ（本地消息表） | 6 进程 | 跨服务一致性有对账兜底 |

M4 之后每一步都必须先触发准入条件，否则不动（见 `decisions/0006-组件准入.md`）。

## 组件引入时序

| 组件 | 首次出现在 | 前置条件 | 需要的 ADR |
|---|---|---|---|
| 无（MySQL + 定时任务） | M0~M3 | — | — |
| 应用日志 + `X-Request-Id` | M0 | — | — |
| 缓存（Redis） | M4 | 详情 QPS > 200 或单表 > 100 万 | 是，记录触发数据 |
| 消息队列 | M5 | 需要削峰或异步解耦 | 是 |
| 分布式追踪 | M6 | 出现"跨服务定位慢"的需求 | 是 |
| 注册中心 + 网关 | M7 | 已经有两个进程 | 是 |
| 分布式事务方案 | M10 | 拆到 order 且出现跨服务写 | 是（优先本地消息表，不是 Seata） |

**同一时刻最多只有一项"新组件"处于试用期。** 两项一起来，出问题分不清是谁。

## 怎么算"拆分成功"

不是"服务能起来"，而是这四条同时成立：

1. 原模块的**契约测试全部通过**，没有为了拆分改接口语义
2. 独立部署：只重启该服务，其他服务不受影响
3. 独立扩容：该服务可以起两个实例，请求能被分摊
4. 故障隔离：该服务挂掉，其他模块的核心链路仍可用（或明确降级）

四条里任何一条不成立，这次拆分只是把代码搬到了另一个进程，多了一份运维成本。

## 拆分时的固定动作

每次拆一个模块，都走同一套流程（避免每次重新发明）：

1. 把该模块的跨模块调用整理成"接口清单"，先做成单体内部的显式接口
2. 契约测试补到覆盖这些接口
3. 新进程只提供这些接口，单体通过 HTTP 调用它，两套实现并存（双跑）
4. 观察一周：错误率、P95、日志里是否有新的跨进程异常
5. 删掉单体里的旧实现，完成拆分

第 3 步的"双跑"是关键：出问题能一条配置切回去，而不是靠回滚发布。

## 常见误区

| 误区 | 后果 |
|---|---|
| 先拆 order（最核心的那个） | 在没有 trace、对账、契约测试时改编排，事故无法定位 |
| 拆分和加功能一起做 | 出问题分不清是新功能还是拆分导致 |
| 为了"架构好看"而拆 | 拆完只多了运维成本，独立部署/扩容/隔离一个都没得到 |
| 一次拆三个模块 | 回归失败时无法二分定位 |
