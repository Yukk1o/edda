# 0005 评论可见性与审核状态解耦

- 状态：**草案**（M2 评论功能启动时定稿，在此之前不要按本文写代码）
- 日期：2026-11-26
- 影响：comment

## 背景

评论需要审核，但审核是慢的（规则匹配 + 可能的人工复核）。
如果"通过审核才落库"，用户提交后要等几秒，会以为失败并反复提交；
如果"落库即公开"，违规内容会有一段时间对外可见。

## 决策

**提交即落库，状态为待审；可见性由状态直接承担。**

| 状态 | 谁能看见 |
|---|---|
| 待审 | 仅作者本人 |
| 通过 | 所有人 |
| 拒绝 | 仅作者本人（附理由码） |
| 删除 | 无人（软删，保留原文用于追溯） |

三条配套规则：

1. 审核异步进行，列表查询只取「通过」或「作者本人」
2. 内容有版本号，**编辑后必须重新审核**，展示按最新版本的判定结果
3. 每次判定写审核流水（机器与人工都记），含规则码与操作人

## 代价

- 用户会看到"审核中"这一中间态，需要前端文案配合
- 需要人工复核队列，误杀必须有申诉入口
- 多一个"待审"索引，列表查询要带状态条件

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 同步审核后才落库 | 阻塞主链路；规则层或模型超时会直接拖死发布接口 |
| 先公开、事后抽检 | 违规内容会有一段时间对外可见，合规风险不可接受 |
| 只用状态机字段，另设"是否公开"开关 | 两个字段必然不同步，最终出现"已通过但不可见"的鬼数据 |

## 备注

评论区的真实违规大头是导流广告（加微信、扫码进群），不是脏话。
联系方式与二维码检测的优先级应高于脏话词库。
