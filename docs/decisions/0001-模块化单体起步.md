# 0001 模块化单体起步，按里程碑演进到微服务

- 状态：已采纳（替代初版「不拆微服务」）
- 日期：2026-11-26
- 影响：全局
- 关联：[`../roadmap.md`](../roadmap.md)

## 背景

目标是**最终形态是微服务**，但起点只有一个人、一个库、零流量。

两种极端都不可取：

- 一次性拆成 6 个服务：在没有任何流量的情况下先承担分布式事务、跨进程排障、独立部署的全部成本，且没有可观测性兜底，出事只能靠猜
- 永远单体：目标落空，而且到真需要拆的时候，代码已经长成拆不动的形状

真正要设计的是**中间那条路**：让系统在单体形态下就保持"可拆性"，然后按压力逐个拆。

## 决策

分三个阶段，每一阶段的产物是下一阶段的前置条件。

### P1 模块化单体（现在）

单进程、单库，按领域分包。模块之间只通过 service 接口与 DTO 交互，实体不出包。

依赖方向**不靠自觉**，由 ArchUnit 在 CI 里守：禁反向依赖、禁跨模块注入仓储、禁循环。
规则写在测试里，`mvn verify` 失败即门禁失败（见 issue 001）。

此阶段刻意不引入：网关、注册中心、配置中心、消息队列。

### P2 可拆性验证（拆分前必须完成）

拆服务之前，单体阶段就要把"拆开之后需要的东西"先建起来，否则拆完立刻失明：

| 前置能力 | 为什么拆之前就要有 |
|---|---|
| 统一请求标识（`X-Request-Id`） | 拆完一次请求跨 3 个进程，没有它无法串日志 |
| 契约测试 | 模块间调用变成跨进程调用，契约必须有自动校验 |
| 接口场景脚本 | 每次拆分都要回归同一套业务链路 |
| 多进程启动能力 | 拆完要能同时起 6 个进程，本地开发环境必须先支持 |

这一阶段在单体形态下看起来"白做"，但它决定了拆分之后你是**可控演进**还是**连续事故**。

### P3 逐个拆分（每次只拆一个）

拆分顺序不是按重要性，是按**依赖方向**：

| 顺序 | 拆谁 | 理由 |
|---|---|---|
| 1 | `course` | 被依赖、无状态、边界清晰，用来验证拆分流程本身 |
| 2 | `auth` | 独立性强，鉴权天然是横向能力 |
| 3 | `coupon` | 依赖 course，但自身无资金副作用 |
| 4 | `enroll` | 与 order 只有一个方向的关系 |
| 5 | `payment` | 开始接触资金，必须有对账兜底 |
| 6 | `order` | **最后拆**，它是编排者，拆它等于重写编排逻辑 |

关键判断：**先拆叶子，后拆编排者。** 编排者拆开才会暴露真正的分布式问题（跨服务一致性、补偿、超时链路），
但那时你已经有了 trace、对账、契约测试和三套已拆服务的经验。

反过来先拆 order，等于在没有任何观测手段的时候直接改发动机。

## 拆分触发条件

不是"到了 P3 就拆"，而是命中条件才拆。任意两条：

1. 某个模块的发布频率与整体差 5 倍以上
2. 某个模块的资源画像与其他模块完全不同（CPU 密集 vs IO 密集）
3. 全量回归时间已经阻碍迭代
4. 出现合规/隔离硬要求（数据物理隔离、独立审计）

## 代价

- P2 的投入在 P1 阶段看不到收益，容易中途放弃——这是这条路线最大的风险
- 每次拆分都会产生一次"临时双写/双读"的过渡期，需要明确的切换与回滚方案
- 拆完之后运维面翻倍：6 个进程、6 份配置、6 套健康检查
- 契约测试与场景脚本必须跟着演进，否则拆完就失去安全网

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 一次性拆成微服务 | 在没有流量与可观测性时承担全部分布式成本，出问题无法定位 |
| 永远单体 | 与目标形态冲突，且代码会逐渐长成拆不动的形状 |
| 用 Spring Modulith 代替 ArchUnit | 能为边界校验引入框架，但边界规则本身很轻，ArchUnit 足够；等真要拆时再评估 |

## 备注

拆服务不是目的。目的是**独立部署、独立扩容、故障隔离**——如果某个模块拆出去之后这三样一个都没得到，
那这次拆分只是增加了运维成本。
