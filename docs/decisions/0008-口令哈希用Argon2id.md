# 0008 口令哈希用 Argon2id，参数显式指定

- 状态：已采纳
- 日期：2026-11-26
- 影响：auth

## 背景

口令必须存单向哈希，不能存可逆密文。选型要回答一个问题：**攻击者拿到库之后，猜一个口令要花多少成本。**

GPU 与专用硬件让 SHA 系列几乎失去意义，bcrypt 也被显存/算力压制得越来越吃力。Argon2 是密码哈希竞赛的胜出方案，其中 Argon2id 兼顾抗侧信道与抗 GPU。

## 决策

用 Argon2id，参数显式写死，不使用框架默认值：

| 参数 | 值 | 说明 |
|---|---|---|
| 内存 m | 19456 KiB（19 MiB） | OWASP 推荐下限 |
| 迭代 t | 2 | 与上面的内存配比是官方推荐的组合 |
| 并行度 p | 1 | 单核足够，避免被容器 CPU 限额拖慢 |
| salt | 16 字节 | 由算法库生成，不自己拼 |
| 输出长度 | 32 字节 | |

编码串自带参数，因此**换参数不需要写数据迁移**：登录验证时按串里的参数算，验证通过后若发现参数低于当前标准，顺手用新参数重算一次并覆盖。

口径统一在 `PasswordEncoder` 一个 bean 上，业务代码只调 `encode` / `matches`，不出现任何算法名。

## 代价

- **内存放大**：每次哈希占 19 MiB。50 个并发登录就是约 1 GiB，容器内存限额必须预留这部分，否则 OOM
- 需要额外依赖（Bouncy Castle 或 JNI 实现），不过两者都是无状态库，符合组件准入
- 比 bcrypt 慢，登录接口的 P99 会被拉长（这是特性不是缺陷）
- 若将来有 FIPS 合规要求，Argon2 不被认可，必须换 PBKDF2

## 替代方案

| 方案 | 相比 Argon2id 的差别 |
|---|---|
| bcrypt（cost 12） | 无内存硬特性，抗 GPU 弱一档；但零额外依赖、无内存放大，实现最简单。若内存约束紧，这是合理退路 |
| scrypt | 同样是内存硬，参数不好调，Java 生态支持弱于 Argon2 |
| PBKDF2 | 只有需要 FIPS 时才选，抗 GPU 最弱 |
| SHA-256 + salt | 绝不可用，GPU 每秒可试数十亿次 |

## 备注

三条不能碰的红线：

1. 口令不进日志、不进 trace、不进异常信息。DTO 上对该字段做 `@ToString.Exclude`
2. 不自己生成 salt，不用固定 salt，不加"全局密钥"来替代 salt
3. 校验失败一律返回同一个错误码与同一句提示，不能区分"用户不存在"和"密码错误"——否则就是账号枚举
