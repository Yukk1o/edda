# 0004 幂等靠持久层唯一性，不靠应用判断

- 状态：已采纳
- 日期：2026-11-26
- 影响：order / payment / coupon

## 背景

下单、支付回调、券核销这三处都会被重复触发：用户连点、网关重试、渠道重复通知。
"先查有没有，没有再插入"在并发下必然失效——两个请求同时查不到，然后都插入。

## 决策

用持久层唯一性做最终保证，应用层只负责优雅处理冲突：

| 场景 | 唯一范围 |
|---|---|
| 下单 | 用户 + 幂等键 |
| 支付回调 | 渠道 + 渠道交易号 |
| 券核销 | 券 + 订单 |

冲突后的行为分两类：

- **下单**：捕获冲突后**重新查出原订单返回**，`code=200`。用户点两下不该看到报错
- **支付回调**：捕获冲突后视为已处理，直接返回成功，不产生任何副作用

## 代价

- 幂等键永久留存，需要一个清理策略（v0 不做，数据量下无所谓）
- 语义宽松：同一个 key 换了请求体，也返回原订单（刻意不校验指纹）
- 依赖数据库唯一索引，未来分库分表时唯一性会变成跨分片问题

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 先查后插 | 并发必失效，是最常见的错误实现 |
| Redis `SETNX` 做幂等 | 多一个中间件；进程崩溃/过期策略会让幂等失效，而数据库不会 |
| 请求体指纹校验 | v0 不需要；它解决的是"同 key 不同语义"，属于误用防护而非幂等 |

## 备注

幂等键的唯一范围必须包含用户 id。只按 key 做唯一，A 用户猜中 B 用户的 key 就能读到别人的订单号。
