# 0007 测试策略：四层，脚本由 AI 辅助但断言必须人写

- 状态：已采纳
- 日期：2026-11-26
- 影响：全局

## 背景

计划用 AI 辅助生成接口测试脚本。这件事能大幅降低写脚本的成本，但有一个明确的失效模式：
**AI 很擅长写出"能跑通"的脚本，却不擅长判断"什么算对"。**

如果脚本只断言 HTTP 200，那它验的是"服务还活着"，不是"业务正确"。
这种脚本比没有更危险——它会给你绿色的假象。

## 决策

四层测试，各自负责不同的失败：

| 层 | 测什么 | 工具 | 谁写 |
|---|---|---|---|
| 1 单元 | 业务规则：状态机迁移、退款判定、金额计算、券匹配 | JUnit | 人写，AI 补用例 |
| 2 边界 | 模块依赖方向、循环依赖 | ArchUnit | 人写一次 |
| 3 契约 | 接口的入参/出参/错误码是否与文档一致 | 手写断言 或 OpenAPI 快照比对 | 人定契约，AI 生成骨架 |
| 4 场景 | 跨接口的业务链路（下单→支付→授权→退款） | Python + pytest + httpx | **AI 生成，人补断言** |

### 场景脚本的三条硬要求

1. **断言必须覆盖三样**：HTTP 状态、关键业务字段、以及一条不变量
   （例如"下单后名额守恒"、"重复回调后授权仍为 1 条"）
2. **可重复**：每个用例自己造数据、自己清理，不依赖执行顺序
3. **可并行**：数据不共享（用随机手机号、随机幂等键），否则并行必冲突

不满足这三条的脚本，宁可不写。

### 脚本与验收的关系

issue 里的验收命令（`curl`）只是给人快速验证用的；**长期资产是脚本**。
每次改动后跑脚本，而不是重新抄一遍 curl —— 两者并存必然漂移，最终 curl 是旧的、脚本是错的。

## 代价

- 场景脚本的维护成本高于单元测试，业务变了要跟着改
- AI 生成的脚本需要人工过一遍断言，省下的是"写代码"不是"想清楚"
- 契约测试在接口频繁变动期会很吵，需要允许"预期内失败并同步更新"的流程

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 全部用 Postman/`.http` 文件 | 人工点击不可回归，无法进 CI |
| 只写单元测试 | 跨接口的链路问题（幂等、状态机、补偿）单元测试覆盖不到 |
| 依赖 AI 全自动生成 + 自动断言 | 断言质量不可控，会产出"绿色但无意义"的测试 |

## 备注

场景脚本放 `tests/api/`，与 issue 编号对应（例如 `test_018_order_idempotency.py`），
这样 PR 与 issue 能互相追溯。
