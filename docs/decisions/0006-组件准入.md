# 0006 组件准入：有状态中间件必须过四问

- 状态：已采纳
- 日期：2026-11-26
- 影响：全局

## 背景

项目最常见的死法不是写不出来，而是第一版就堆满中间件：缓存、消息队列、搜索、调度中心、链路追踪。
每一个都"以后肯定用得上"，结果是每个都要运维、都会挂、都没人真正掌握。

## 决策

按"是否产生运维面"分成两类，区别对待：

| 类型 | 例子 | 准入 |
|---|---|---|
| 有状态中间件 | Redis、MQ、ES、调度中心、注册中心、分布式事务 | 必须过四问 |
| 无状态库 | 校验、序列化、迁移工具、连接池 | 随手可用，但引了必须用 |

四个问题，全部能答才允许引入：

1. 不用它，最小方案能撑到什么时候？（要数字，不要"应该不够"）
2. 它挂了，业务怎么降级？
3. 它的部署、备份、升级、监控谁承担？
4. 半年后想去掉它，要改多少地方？

有状态组件的引入必须写一条 ADR，记录当时的触发条件与预期收益。

## 代价

- 短期会在应用层重复造一些轮子（比如用定时任务代替调度中心）
- 有些能力会做得比现成组件粗糙（比如用数据库扫表代替消息队列）
- 需要定期做"组件审计"，删掉引了没用的依赖

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 预置全套中间件 | 每个组件都会成为新的故障源和运维负担 |
| 完全不引入 | 该上的时候不上，会把简单问题做成硬编码（例如用 sleep 轮询代替延迟任务） |

## 备注

允许"事后反悔"：组件引入后如果没有产生预期收益，应当在一个迭代内移除，而不是留着"以后用"。
