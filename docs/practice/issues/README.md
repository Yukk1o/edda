# Issue 索引

> 编号 = 实现顺序，**只增不改、不复用**。想让某个 issue 排到前面，就新建一个，不要改别人的编号。

---

## 拆分标准

一个 issue 必须同时满足三条，否则继续拆：

1. **一次会话能做完**（半天以内）
2. **有且仅有 1 条可执行的验收**（能复制命令跑，不是"检查逻辑正确"）
3. **不跨两个领域**（下单里不要顺手改券表）

反过来，如果拆到"加一个字段"这种粒度就过头了——那种直接并进上下文相近的 issue。

## 标题规则

`[领域] 动词 + 对象`，例如 `[order] 实现下单幂等键`。

领域固定几个：`infra` / `auth` / `course` / `coupon` / `stock` / `order` / `payment` / `enroll` / `comment` / `recon`。

## 每个 issue 固定六段

```
## 背景      为什么做（一句，说清痛点）
## 范围      做什么（列点，不超过 5 条）
## 不做      明确排除的（防范围蔓延）
## 验收      必须全过，带命令或明确断言
## 依赖      前置 issue 编号
## 备注      技术决策、坑、参考
```

`## 不做` 这一节最有价值——它让 review 时有明确边界，也防止你自己几天后往上加需求。

## 使用方式

1. 在 GitHub 建 milestone：`M0 骨架` / `M1 卖课闭环` / `M2 评论合规` / `M3 对账`
2. 按编号顺序建 issue（标题直接抄上表）
3. 开分支时用 `feat/018-order-idempotency` 这种命名，前缀带编号
4. PR 描述里写 `Closes #18`，合并后自动关闭
5. **一次只开一个 issue**。同时开三个，等于三个都做不完

## 样例

- `001-初始化工程.md` —— 最小、最机械的一个，看结构
- `018-下单幂等.md` —— 业务最重的那个，看验收怎么写
