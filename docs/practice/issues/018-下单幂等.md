# [order] 下单幂等

> M1 卖课闭环 · 依赖 017 · 预计 2~3 小时

## 背景

用户连点两下、网关重试、客户端超时后自动重发——这三种情况每天都会发生。
没有幂等，就是两笔订单、两次扣名额、两次授权。**这是下单接口唯一的正确性底线。**

## 范围

- `POST /orders` 必须带 `Idempotency-Key` 请求头（1~64 字符），缺失返回 `400001`
- 同一用户 + 同一幂等键，只允许存在一张订单（持久层唯一性兜底）
- 键冲突时**返回原订单**，`code=200`，不报错、不提示"重复"
- 幂等键不再有"过期清理"逻辑（v0 不做，见「不做」）

## 不做

- 不做请求体指纹校验（同一个 key 换了 body 也不报错，直接返回原单——这是刻意的宽松）
- 不做跨接口幂等（支付、退款各有各的幂等，不共用 key）
- 不用 Redis 存 key（唯一性交给数据库，见备注）
- 不做过期清理任务（键会一直留着，v0 数据量下无所谓）

## 验收

四条必须全过。

**1. 缺 key 被拒**

```bash
curl -s -X POST http://localhost:8080/api/v1/orders \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"packageId":1001}' | jq -r .code
# 期望 400001
```

**2. 同 key 连发 5 次，返回同一张单**

```bash
for i in $(seq 5); do
  curl -s -X POST http://localhost:8080/api/v1/orders \
    -H "Authorization: Bearer $TOKEN" \
    -H "Idempotency-Key: idem-001" \
    -H "Content-Type: application/json" \
    -d '{"packageId":1001}' | jq -r .data.orderNo
done | sort -u | wc -l
# 期望 1
```

**3. 并发同 key（50 并发）**

期望：订单表里该用户该 key 只有 1 行；名额冻结只增加 1；无 5xx。

**4. 不同 key 并发抢最后 1 件**

期望：1 个成功、1 个 `409001`；`可售=0，冻结=1，已售=0`；订单只有 1 张。

## 备注

**为什么用唯一索引而不是先查后插**：并发下两个请求同时"查不到"，然后都插入 —— 先查后插必然失效。
唯一索引是数据库层面的原子保证，不依赖应用判断。

**冲突后必须重新查一次**：捕获到唯一键冲突，说明另一个事务刚提交，此刻能查到。直接返回"已存在"而不查，
前端拿不到订单号。

**别把幂等做成 409**：用户点两下不该看到报错。`code=200 + 原订单`才是对的交互。

**键的唯一范围要带 user_id**：只用 key 做唯一，A 用户猜中 B 用户的 key 就能拿到别人的订单号。
