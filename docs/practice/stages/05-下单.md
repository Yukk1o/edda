# Stage 05 · 下单：幂等与名额冻结

> 前置：Stage 04（名额冻结）已通过。
> 这一阶段是整个项目最容易翻车的地方，请慢一点。

## 目标

同一个用户带同一个幂等键重复提交，**无论多少次、无论并发**，最终只有一张订单、只冻结一份名额。

## 规格

### 接口

```
POST /api/v1/orders
Header: Authorization: Bearer <session>
Header: Idempotency-Key: <客户端生成的唯一串，1~64 字符>
Body:   { "packageId": 1001, "userCouponId": 2001 }   // userCouponId 可为 null
```

成功响应（HTTP 200）：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "orderNo": "20261126193012345678",
    "totalAmount": 299.00,
    "discountAmount": 20.00,
    "payAmount": 279.00,
    "expireAt": "2026-11-26T19:45:12+08:00"
  }
}
```

### 规则

| 场景 | 行为 |
|---|---|
| 首次提交 | 创建订单，冻结名额，锁定券，`expireAt = now + 15 分钟` |
| 同 key 再次提交 | **返回原订单，code=200，不报错** |
| 缺 `Idempotency-Key` | `400001`，不产生任何副作用 |
| 名额不足 | `409001` 售罄，名额不变，不产生订单 |
| 券不可用 / 已用 | `409002` / `409003`，**名额必须已回滚** |
| 已拥有该课程 | `409005`，不扣名额 |

### 执行顺序（这是本阶段真正的考点）

```
1. 只读校验：班期在售？还在售卖期？用户没买过？
2. 只读试算：券是否可用、能减多少（纯读，不影响状态）
3. 冻结名额        ← 第一个写操作
4. 锁定券          ← 第二个写操作
5. 写订单 + 明细   ← 第三个写操作
```

任何一步失败，前面已经发生的写操作都要撤销。**顺序不能变**：把写操作尽量往后放，能让"只读校验失败"这种最常见的错误不产生任何副作用。

### 禁止

- 引入 Redis / MQ（本阶段用不上，见 `../../decisions/0006-组件准入.md`）
- 用 `synchronized` 或进程内锁（单机有效，后面必翻车）
- 用 `select ... for update` 锁整张表（会成为下一个瓶颈）

## 验收

四条必须全过。前三条用 `curl`，第四条用并发工具（`hey` / JMeter / 自己写循环都行）。

**1. 正常下单**

```bash
curl -i -X POST http://localhost:8080/api/v1/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: test-001" \
  -H "Content-Type: application/json" \
  -d '{"packageId":1001,"userCouponId":null}'
```

期望：200，返回 `orderNo`；名额 `冻结 +1`；订单状态 `CREATED`；`expireAt` 是 15 分钟后。

**2. 同 key 连发 5 次**

```bash
for i in 1 2 3 4 5; do
  curl -s -X POST http://localhost:8080/api/v1/orders \
    -H "Authorization: Bearer $TOKEN" \
    -H "Idempotency-Key: test-001" \
    -H "Content-Type: application/json" \
    -d '{"packageId":1001,"userCouponId":null}' | grep -o '"orderNo":"[^"]*"'
done
```

期望：5 行输出**完全相同的订单号**；名额定冻结只加 1。

**3. 并发同 key**（50 个并发，同一个 key）

期望：只产生 1 张订单。任何"两张订单"或"扣了两次名额"都算失败。

**4. 名额只剩 1 件，两个不同 key 并发**

期望：1 个成功、1 个返回 `409001`；最终 `可售=0，冻结=1，已售=0`（守恒）。

## 提示（卡住再看）

<details>
<summary>幂等的两种实现方式，选哪个</summary>

- **唯一索引 + 捕获冲突**：把 `(用户, 幂等键)` 做成唯一。冲突时**查回已有订单返回**。可靠性最高，推荐。
- **先查再插**：并发下必然失效（两个请求同时查不到，然后都插）。不要用。

关键细节：捕获冲突后要**重新查一次**再返回，因为冲突意味着另一个事务刚提交，此刻能查到。
</details>

<details>
<summary>名额怎么扣才不会超卖</summary>

用一条带条件的更新，把"判断"和"修改"压进同一个语句：

```
可售 > 0 时才把 可售-1、冻结+1
```

影响行数为 0 就代表没抢到。不要"先查再改"。
</details>

<details>
<summary>失败回滚后，名额对不上怎么办</summary>

先别急着写补偿逻辑。**先确认你能不能观测到不一致**：写一个临时接口，把 `可售+冻结+已售` 和总名额对比。看不到就谈不上修。
</details>

## 常见错误

| 现象 | 原因 |
|---|---|
| 重复提交返回 409 | 把幂等冲突当成业务错误了。用户点两下不该看到报错 |
| 名额扣了但没订单 | 写操作顺序错了（先扣名额、后校验券） |
| 并发下出现两张订单 | 靠应用层"先查再插"，没有唯一性兜底 |
| 用 `synchronized` 通过了自己的测试 | 单机测试通过 ≠ 正确，压测和多实例会暴露 |
| 券锁了但订单没落库 | 没有把"锁券"和"写订单"放进同一个失败回滚路径 |
